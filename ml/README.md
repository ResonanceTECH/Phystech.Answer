# ML-сервис

RAG-конвейер Физтех.Ответ на Go (только стандартная библиотека):
структурный чанкинг → гибридный BM25/vector-поиск → декомпозиция
составных вопросов → H2O-реранкинг → учёт изменяющих актов →
структурированный ответ с проверенными цитатами.

## Запуск

```bash
cd ml
go run ./cmd/ml        # http://localhost:8000
```

Конфигурация — через `.env` (см. `.env.example`).

## Как это работает

1. **Индексация.** Бэкенд при старте и при CRUD документов шлёт их сюда
   (`POST /api/sync`, `PUT/DELETE /api/documents/{id}`). Документ режется
   на чанки по структурным границам (пункты «3.4.», разделы), каждый чанк
   получает эмбеддинг.
2. **Поиск.** Для каждого запроса выполняются BM25 с русским стеммингом и
   векторный поиск, списки объединяются RRF. Составной вопрос предварительно
   разбивается на 2–3 независимых запроса.
3. **Реранкинг.** H2O-Lightning-4B оценивает, отвечает ли каждый кандидат
   на исходный вопрос или один из подвопросов. Эта же оценка служит
   evidence gate и отделяет реальное отсутствие ответа от перефразировки.
4. **Ответ.** LLM получает только отобранные фрагменты и возвращает JSON:
   summary, steps, notes, conflicts и missing. Для процедур steps обязателен;
   ссылки вне диапазона реальных фрагментов удаляются. Если LLM недоступна,
   сервис возвращает подтверждённые выдержки.

## API

| Method | Path                  | Описание                                        |
|--------|-----------------------|--------------------------------------------------|
| GET    | /health               | health + размер индекса                          |
| GET    | /api/documents        | список проиндексированных документов (метаданные)|
| PUT    | /api/documents/{id}   | проиндексировать документ `{title, content, tags}` |
| POST   | /api/documents        | то же, id в теле запроса                         |
| DELETE | /api/documents/{id}   | удалить документ из индекса                      |
| POST   | /api/sync             | `{documents: [...]}` — полная пересборка индекса  |
| POST   | /api/ask              | `{question}` → `{answer, sources: [{documentId, title, section, excerpt, score}]}` |
| POST   | /api/retrieve         | поиск без генерации (отладка и eval)            |
| POST   | /ask                  | алиас для совместимости с бэкендом              |

## LLM и эмбеддинги

Генерация и эмбеддинги используют OpenAI-compatible endpoint'ы. Дефолт —
локальный Ollama (`http://localhost:11434/v1`):

```bash
ollama pull qwen3.5:4b  # чат, декомпозиция
ollama pull bge-m3      # эмбеддинги
```

Decision-реранкер использует H2O-Lightning-4B через llama.cpp
`/v1/systemone`; адрес задаётся `DECISION_BASE_URL`, режим —
`RAG_RERANK=decision`. Для внешних API задайте `*_BASE_URL` и `*_API_KEY`.
`LLM_BASE_URL=off`, `EMBED_BASE_URL=off` или `RAG_RERANK=off` отключают
соответствующий компонент — сервис продолжает работать в деградированном
режиме.

## Хранилище

Индекс — в памяти + JSON-снимок (`INDEX_PATH`, атомарная запись).
Брутфорс-косинус по тысячам чанков — мгновенно. При росте корпуса
логично переехать на Postgres + pgvector: интерфейс `store.Store`
для этого уже очерчен.

## Проверка

```bash
curl localhost:8000/health
curl -X POST localhost:8000/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Как открыть ФЛС для научного проекта?"}'
```

Контрольный end-to-end замер:

```bash
go run ./cmd/eval -url http://localhost:8000 -questions ../eval/questions.jsonl \
  -out ../eval/results-e2e-ours.md -stage e2e \
  -configs hybrid+decide+amend+decomp
```

На последнем подтверждённом прогоне: верный статус 39/39, нужный документ
в источниках 91%, нужный пункт 19/19. Полная таблица находится в корневом
README и `eval/results-e2e-ours.md`.
